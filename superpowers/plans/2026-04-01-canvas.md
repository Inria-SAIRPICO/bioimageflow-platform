# Canvas (Node Programming Interface) — TDD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the central DAG editor canvas where users visually construct workflows by placing tool nodes, connecting them with edges, and interacting with the graph. Includes custom node/edge rendering, pins, selection, copy/paste, undo/redo, status reconciliation, canvas controls, and drop-from-tools-panel.

**Architecture:** The canvas wraps Vue Flow with custom node and edge components. Vue Flow owns the graph state (nodes, edges, positions). A `useGraphSync` composable debounces changes and sends them to `PUT /graph` for server validation. A `useUndoRedo` composable maintains a snapshot stack. A `useStatusReconciliation` composable manages provisional vs authoritative node states, handling desaturated colors during the debounce window and consuming WebSocket `node_state` messages. Node status is reconciled between client-side provisional states and server-authoritative states from validation responses and WebSocket messages.

**Tech Stack:** Vue 3, TypeScript, Vue Flow (`@vue-flow/core`), Vitest, Playwright

**User Verification:** NO

**Prerequisites:** Project scaffolding complete, backend graph models defined (GraphState, NodeState, Edge, ValidationResult), Pinia `toolRegistryStore` exists (from Tools Panel plan Task 11), API client available.

**Vue Flow Testing Note:** Components that use Vue Flow's `Handle` component require a `VueFlow` provider wrapper in tests. Create a shared test helper `frontend/src/test-utils/wrapWithVueFlow.ts` that wraps a component in a `<VueFlow>` parent, providing the necessary injection context. Use this helper for all InputPin, OutputPin, ToolNode, and edge component tests.

## Integration Points

The canvas interfaces with four other subsystems:

- **ToolsPanel:** Drag-drop via HTML5 Drag API. ToolsPanel sets MIME type `application/bioimageflow-tool` with the tool class name as data. CanvasView listens for `drop` events, reads the MIME data, and creates a node at the drop position.
- **NodePanel:** Selection sync. CanvasView emits `node-selected` with an array of selected node IDs. NodePanel listens and displays the parameter editor for the selected node(s). Single selection shows the full editor; multi-selection shows bulk actions only.
- **Execution store:** Graph locking during execution. When execution is running, the canvas must prevent structural edits (add/remove nodes/edges) but still allow panning and zooming. The execution store exposes an `isRunning` ref that CanvasView watches.
- **WebSocket:** `node_state` messages for real-time status updates. The `useStatusReconciliation` composable subscribes to the WebSocket and updates node border colors when authoritative status arrives (e.g., running, executed, failed).

### Task 3: Undo/Redo Composable

**Files:** `frontend/src/composables/useUndoRedo.ts`, `frontend/src/composables/__tests__/useUndoRedo.test.ts`

**Exports:**
- `useUndoRedo<T>(maxSize?: number)` — Returns `{ push, undo, redo, canUndo, canRedo, clear }`

**Behavior:**
- Generic over state type T. Uses `structuredClone` for snapshot isolation.
- `push(state)` adds to undo stack, clears redo stack. Evicts oldest entry when exceeding maxSize.
- `undo()` returns previous state (or undefined if at bottom). Moves current to redo stack.
- `redo()` returns next state (or undefined if at top). Moves it back to undo stack.
- `canUndo`/`canRedo` are computed refs.
- `clear()` resets both stacks.

**Tests to write:**
- Initial state: canUndo and canRedo both false
- Push enables undo
- Undo restores previous state, returns it
- Redo restores undone state
- Push after undo clears redo stack
- Respects max stack size (oldest entries evicted)
- Undo/redo on empty stack returns undefined
- Clear resets everything

### Task 4: Graph Sync Composable (Debounced Validation)

**Files:** `frontend/src/composables/useGraphSync.ts`, `frontend/src/composables/__tests__/useGraphSync.test.ts`

**Exports:**
- `useGraphSync()` — Returns `{ syncGraph, flushNow, patchParameters, validationResult, isPending }`

**Behavior:**
- `syncGraph(graph)` debounces at 300ms, then calls `PUT /api/v1/graph` with the graph payload. Supersedes any in-flight request (uses an incrementing request ID to ignore stale responses).
- `flushNow()` cancels the debounce timer and sends immediately.
- `patchParameters(nodeId, parameters)` calls `PATCH /api/v1/graph/nodes/{nodeId}/parameters` for lightweight single-node updates.
- `validationResult` is a ref containing the latest `ValidationResult` (valid, node_statuses, errors).
- `isPending` is a ref that is true while a request is in flight.

**Tests to write (mock `api.put` and `api.patch`, use fake timers):**
- Multiple rapid syncGraph calls result in only one PUT after debounce
- Cancels/supersedes in-flight request when new edit arrives
- Returns validation result in the ref after resolution
- flushNow sends immediately without waiting for debounce
- patchParameters uses the lighter PATCH endpoint with correct payload shape

### Task 9: Status Reconciliation Composable

**Files:** `frontend/src/composables/useStatusReconciliation.ts`, `frontend/src/composables/__tests__/useStatusReconciliation.test.ts`

**Dependencies:** Task 4 (useGraphSync, for validationResult)

**Exports:**
- `useStatusReconciliation(nodes: Ref<Node[]>, validationResult: Ref<ValidationResult | null>, wsMessages: Ref<NodeStateMessage[]>)` — Returns `{ reconciledStatuses, isReconciling }`

**Behavior:**
- Manages two status layers: **provisional** (client-side, set immediately on user edits) and **authoritative** (from server validation responses or WebSocket node_state messages).
- During the debounce window (after an edit, before server response), nodes display **desaturated colors** to indicate provisional status. This is encoded via a `provisional: boolean` flag per node that the ToolNode component uses to apply a CSS desaturation filter.
- When `validationResult` updates, authoritative statuses overwrite provisional ones. The `provisional` flag is cleared.
- When a WebSocket `node_state` message arrives (containing node_id and new status), it updates the authoritative status for that node immediately, even between validation cycles.
- Status priority: WebSocket message > validation response > provisional edit.
- `isReconciling` is a computed ref that is true when any node has a provisional status awaiting confirmation.

**Visual encoding (for ToolNode to consume):**
- Provisional nodes: apply `filter: saturate(0.4)` CSS to the node border color
- Authoritative nodes: full saturation border color per status

**Tests to write:**
- Returns authoritative status when no pending edits
- Returns provisional status during debounce window
- Authoritative status overwrites provisional on validation response
- WebSocket message updates status immediately
- WebSocket message takes priority over stale validation response
- isReconciling is true when provisional statuses exist, false after reconciliation
- Multiple rapid edits: only the latest provisional state matters
