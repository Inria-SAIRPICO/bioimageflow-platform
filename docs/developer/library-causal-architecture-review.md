## Architecture and ownership

Core provides lightweight declaration/value APIs, current task/result and executable-origin codecs, local worker execution, portable viewer metadata and numeric allocation/lease storage.
BIF builds editable/captured graphs and schemas, compiles aligned local work, admits environment/SDK/configuration, schedules Direct or managed work, validates correlated results and publishes immutable scientific records.
Storage owns record/data/asset integrity and selected addresses; run/result presentation is a separate projection and must carry its selected record binding.
Controller-owned numeric scopes preown output namespaces; workers borrow mapping/allocation grants, while accepted references and NumPy views retain strong owners independently of temporary Workflow lifetime.
Local attached return/bundle APIs live inside mixed launcher modules; their repository locks, schemas, asset and hydration ownership remain in scope.
Nine companion packages supply table/IO/measurement/segmentation/restoration/spot/tracking/binary/FLIM science through those APIs; optional scientific dependencies are capabilities, not base-import obligations.
CLI/logging/viewer derivation and release/CI tooling consume the same identity/refusal/resource contracts.
Actual Parsl/Dask/remote/PSI-J/SSH/site executor features are excluded; importing a shared DTO or using local result code does not certify those executors or justify deleting them.

The desired clean design has one authority at each transition: effective definition/config, resolved schema, exact executable origin, consumed-row association, scientific cache identity, selected record binding and acquired resource lease.
Most current architecture risks arise where two representations are consulted independently or ownership is published after an effect.
These cross-layer mechanisms are consolidated below; a Node/compiler/worker manifestation does not become three bugs.
