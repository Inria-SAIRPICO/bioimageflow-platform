# Workflow loading optimization plan

Make workflow loading, validation, planning and execution setup reuse admitted package facts instead of repeatedly rediscovering the Python environment and proving unchanged code.
The default contract is that installed packages and application/worker environments stay unchanged between controlled installation, update, recreation and restart boundaries.
Editable workflow tools remain supported through fresh source capture and explicit reload.
Scientific cache correctness continues to cover tracked tool code, declarations, parameters, selected upstream records and runtime content.

This is an implementation plan for the Core/SDK library, its affected tool packages and the platform.
It does not authorize changing the user's workflows, deleting existing results, publishing packages or deploying an application release.
Asynchronous canvas presentation is an optional later improvement; reducing synchronous work is the primary deliverable.

## Replacement guarantees

### Installed packages and environments

An installed tool generation is identified by its canonical selected store root, package/version and admitted content digest.
The process holds its admitted manifest, source/declaration identity and class objects until explicit invalidation or restart.
Installation integrity and scientific identity remain separate: validate the complete RECORD at admission, but derive scientific content identity from the existing finite executable-source inputs, not generated bytecode or installation metadata.
Generation counters and process identities control lifetime; they are not scientific cache-key material.
Equal admitted content and effective inputs retain equal scientific identity across restarts or equivalent recreation.

Validate containment, selected distribution/version, complete installation manifest and declared compatibility when first admitting an installation and after controlled replacement.
Load code from that accepted installation and retain its identity with the actual classes; never hash newer disk bytes and attach that identity to old resident classes.
Do not repeatedly hash RECORD members, reconstruct distribution ownership, inspect every loaded module or attest bytecode during ordinary class lookup, planning or dispatch.
Remove those ongoing guarantees and their redundant implementation paths, rather than retaining an expensive default alongside a new opt-in fast mode.

The application environment is fixed for a process lifetime.
Platform tool installations continue using host-provided declaration dependencies; heavy Processing dependencies belong in their declared worker environments.
For SDK installations that include controller dependencies, admit the chosen dependency ownership once and refuse incompatible selections in the same process; multiple tool versions remain supported, but independent incompatible versions of a shared Python dependency do not become isolated merely through scoped tool names.
Preserve declared compatibility checking and deterministic import selection, including lazy imports, without promising continuous detection of arbitrary `sys.modules` or filesystem mutation.
A controller dependency change requires application restart; it must not be represented as an ordinary tool-class hot reload.

Reuse Wetlands' existing recipe/content receipts, generation checks and lifecycle guard.
Cache admitted worker identity for the ready generation; controlled recreation closes the old pool and invalidates associated receipts before new dispatch.
Do not add a second environment manager, persistent generation database or new Wetlands protocol unless inspection demonstrates an essential missing public operation.

External in-place package edits, independent package-manager changes to a live environment and monkeypatching are unsupported until the caller uses the supported reload/restart boundary.
No automatic detection or scientific correctness claim applies to such mutations during an admitted lifetime.
Validation errors, archive containment, record corruption detection, explicit dependency conflicts and runtime ownership remain supported behavior.

### Editable tools

Keep editable sources separate from installed packages.
At compilation/execution admission, capture current contained source bytes and derive their content identity; watchers improve responsiveness but never substitute for this capture.
Compile the captured bytes under the existing content-derived module identity, and give the worker the same captured source generation.
Deduplicate source capture and parsing within an operation and reuse unchanged content within a bounded cache.
An edit to a represented helper or callback source changes that generation; a syntax error remains visible and blocks execution instead of silently selecting an older class.
An already admitted run may finish against its captured bytes, while the next run captures the new generation.
Installed inherited owners use their admitted installed generation; editable owners participate in the captured source set.
Retain the existing finite source boundary: selected package Python members, their represented ancestors and inherited constructor/callback owners.
Do not promise automatic tracking of arbitrary imported helpers, external assets or transitive Python state outside that set; those retain explicit declared-version/invalidation responsibility.

### Cache identity and existing data

Keep per-node effective parameters, declarations, column/DataFrame bindings, output contracts and selected upstream record identities current.
Reuse only the package/class portion of executable identity; do not cache arbitrary instance state or plan results by class name.
Retain the existing finite source and runtime-content identity inputs, calculated once per supported generation rather than repeatedly attested against mutable state.
Do not add timestamps, process-local generations or filesystem paths to scientific keys.

Prefer retaining current key representation when its fields can be computed from admitted facts.
If simplifying identity requires a representation change, make one explicit execution/cache contract version change, test old/new separation and accept a one-time cache miss.
Do not translate old keys or relabel old results as newly verified.
Keep existing records, retained outputs and export/read APIs intact; no graph/draft migration or cache deletion is required.
Existing installations are admitted lazily on first use after restart; no mass reinstall or persistent receipt migration is needed.

## Implementation phases

### Phase 1 Establish a repeatable baseline and freeze interfaces

The lead chooses the release source, records platform/library revisions and artifact hashes, and creates task-owned worktrees under `.worktrees/` where needed.
Do not share environments, caches, runtime state or build outputs, and preserve the current dirty platform files.
Use read-only inspection of the user's Fish Analysis workflow and disposable copies/ordinary fixtures for execution, installation and cache mutation tests.

Add a focused benchmark harness with phase timings for discovery, saved loading, compilation, validation, planning, first canvas presentation and Run setup before scientific callbacks.
Record cold-process and warm-process samples separately, with missing-runtime, empty-cache and populated-cache cases.
Use at least five fresh-process and ten warm-operation samples, medians and ranges, the same fixture/environment and alternating baseline/candidate order where practical.
Capture operation counts separately from uninstrumented timings; profiler overhead must not become the performance result.

Freeze a small internal admission interface shared by Core and SDK: immutable installed/source facts, dependency inventory, class identity, explicit invalidate/reload, and existing runtime receipt lifetime.
Document who owns each cache and its eviction/invalidation before parallel implementation begins.
Prefer extending `ExecutableMetadata` and existing primary/source objects over creating another public proof format.
Specify the public SDK boundary the platform will call for lookup and controlled invalidation; keep Core's shared internals behind it.

**Exit:** verified source/artifact baseline, reproducible harness and reviewed lifetime/API decisions.

### Phase 2 Simplify library admission and identity

Core ownership is `packages/bioimageflow-core/bioimageflow_core/`: `import_context.py`, `primary_content.py`, `executable_identity.py` and `worker_origins.py`.
SDK ownership is `packages/bioimageflow/bioimageflow/`: `installation.py`, `tool_loader.py`, `worker_origins.py`, `workflow/materialization.py`, `engine/identity_runtime.py`, `engine/planning.py` and `env_manager.py`.
These are paths in the selected release lineage, not guarantees about the older sibling working tree.

1. Reuse a process-lifetime application distribution/import inventory and per-generation parsed installation/member facts.
   Resolve inherited installed owners from that inventory; eliminate the 22 repeated global scans through `primary_content._distribution_member`.
2. Return admitted classes directly from a matching loaded installation generation.
   Share package capture across all classes and nodes, and cache source AST/code indexes by content and interpreter/contract version only where still needed for editable admission.
3. Remove recurring whole-package bytecode/resident-module attestation for stable installed code and recurring global ownership scans at context entry/exit.
   Retain initial selection/compatibility checks, safe import-context restoration and source-generation binding.
   Worker class/instance reuse must remain bound to admitted origin and runtime generation; instance construction and scientific callbacks must not be replayed for validation.
4. Keep live cache selection and record-integrity reads per plan operation.
   Reuse admitted executable facts across compilation, planning and execution through explicit lifetime ownership instead of privately copying platform caches into the SDK.
5. In planning, determine missing runtime and unresolved upstream status before requesting unnecessary executable detail.
   Compute pending diagnostic signatures from cheap admitted facts; `NodePlan.logical_signature` is a public diagnostic field, so omitting it requires an explicit tested API change even though it is not a reusable cache token.
   Preserve strict executable/runtime admission before actual reusable lookup or dispatch and preserve node-attributed definition errors from compilation.

Keep multiple selected package versions and exact carried bindings working.
Support same-package refresh through explicit invalidation/reload after closing affected execution/worker ownership; incompatible controller dependency changes require restart.
A refresh or uninstall must wait for or refuse affected active ownership rather than cancelling admitted runs implicitly.
A failed refresh cannot advertise an unaccepted new generation or silently execute the old version when the caller requested the new one.
Use existing lifecycle locks to serialize publication, invalidation and dispatch rather than adding another independent locking scheme.
The current scoped module name contains package/version but not the store root: define how lookup rejects a resident class from another root and how controlled retirement permits a new root.
Workspace switches must invalidate the selection without unloading code still owned by an admitted run; retained runs keep their original store/runtime authority until drainage.

**Exit:** the supported installed/editable contracts pass on Direct and actual local Wetlands, and operation-count tests demonstrate that repeated warm lookups do not repeat environment/package admission.

## Correctness and performance acceptance

Use existing library tests as starting points: `tests/unit/tool_loader/`, `tests/unit/worker_protocol/test_import_context.py`, `test_origin_construction.py`, `test_selected_primary_attestation.py`, `tests/unit/test_executable_identity.py`, `test_runtime_admission_preparation.py` and `tests/integration/runtime_cache/`.
Select exact tests from the verified release checkout, not the obsolete sibling tree.
Exercise the public APIs and ordinary imported fixture packages so pytest rewriting is not mistaken for executable source authority.

Required scientific/lifecycle controls are:

- Repeated opening/planning executes no scientific callback and starts/provisions no worker environment.
- Equal supported code, runtime content, parameters and upstream selections preserve cache identity; changing a tracked source/helper, declared parameter/default, output contract or selected upstream record produces the appropriate miss.
- Repeated instances/nodes share installed facts while retaining their own parameters and supported declaration differences.
- Two package versions and same-named local sources resolve exactly; an incompatible shared controller dependency is refused at admission.
- The same package/version in two store roots cannot borrow the other root's admitted classes; workspace switching and switching back preserve retained-run ownership and select current store content for new runs.
- Explicit reload/restart sees replaced installed content, and editable changes between runs use the new captured bytes; an admitted run and resident worker cannot acquire mismatched source/key generations.
- Controlled environment recreation invalidates the old receipt/pool while identical runtime content does not gain a different scientific identity merely from a new generation ID.
- Failed install/reload, uninstall, concurrent admission and generation retirement cannot leave an apparently usable half-published package or stale dispatch authority.
- Cache hits, corrupt current pointers/records, nested provider identities, Clear races, parameter edits and retained-result export keep their existing semantics.
- First-party representative numerical outputs match on tiny deterministic data, including mapped and collective behavior, nested workflows and an actual Wetlands worker; mock-only success is insufficient.

Performance acceptance has two parts.
First, deterministic operation-count tests require one environment inventory per admitted application environment and at most one package/RECORD/content admission per installation generation in each owning process, with no repeated whole-environment scans or installed bytecode attestation on warm opening/planning/dispatch.
Editable source capture/parsing is deduplicated within each operation; unchanged content may reuse the bounded cache, and eviction may legitimately require parsing again.
Second, paired uninstrumented measurements must show lower medians for compilation, planning, projected draft loading and Run setup beyond observed baseline run-to-run variation, without a material cold-admission regression hidden by moving work to discovery.
Record cold launch plus first open as well as warm open; report populated-cache integrity cost separately.
Phase 1 sets fixture-specific timing thresholds from its measured variation before optimization, rather than inventing a speed multiplier now.
If reduced call counts do not yield a meaningful user-visible improvement, inspect the remaining measured bottleneck before declaring success or adding asynchronous UI.

During library implementation, run exact affected tests and the selected revision's documented lint/type/import-boundary checks, then its ordinary local CI selectors and affected artifact/runtime gates.
During platform implementation, use `scripts/test focus ...` and the smallest applicable completion check from `docs/testing.md`; runtime/dependency/API increments require `scripts/test check app`.
Use `scripts/test quick` only for intermediate increments not immediately followed by a subsuming check.
Final completion includes `scripts/test full` because this task changes package loading/external compatibility, plus `scripts/test check docs`; do not stack subsumed app/browser/certification lanes immediately before full.
Reproduce exact failing browser tests before wider lanes, retain successful unaffected phases, and report command, result, duration, source revision and every skipped/deselected/blocked phase.

## Agent orchestration and integration gates

The lead/integrator owns the contract, baseline, cross-repository source selection, API decisions, integration, release coordination and final report.
Use at most four concurrent agents including the lead, and no nested delegation by default.
Agents receive explicit file ownership, immutable dependency inputs, tests and exit criteria; they do not edit another agent's files or independently change the shared contract.

| Stage | Concurrent roles | Dependency gate |
| --- | --- | --- |
| Baseline and contract | Lead plus one bounded investigation/test agent if useful | Verified release source, benchmarks and cache/lifecycle API agreed before implementation |
| Library implementation | Lead, Core owner, SDK owner | Core and SDK work in parallel only after the shared admission interface is fixed; separate files/commits |
| Platform preparation | Platform owner may occupy the fourth slot | May prepare fixtures and lifecycle integration against the agreed interface; final adoption waits for integrated artifacts |
| Independent review | Lead plus a fresh reviewer; authors remain available for fixes | Review integrated code, contract changes, scientific controls and performance evidence; do not let an author review their own scope |
| Publication and adoption | Lead with one platform owner as needed | Exact artifacts and CI accepted before release; published dependencies verified before final platform certification |

Use separate task worktrees when concurrent edits or isolation require them, with independent environments and runtime roots.
The lead integrates dependency-ordered commits and alone edits overlapping specifications/version/lock/release files unless explicitly delegated.
Commit only task-owned changes; the new plan is an intended documentation deliverable, while temporary benchmark output and review working notes remain uncommitted.
Retire only merged task-owned worktrees using the repository's move-to-trash and prune procedure.

The independent reviewer must specifically challenge hidden mutation guarantees, duplicate proof/caching systems, stale class versus disk identity, generation fencing, unsupported compatibility claims and benchmark cost shifting.
Authors implement accepted corrections, and the reviewer checks the revised result before the lead accepts the gate.
The current planning task uses a fresh reviewer to improve this plan before implementation begins.

The installed/editable split and narrowed mutation guarantee are already accepted scope decisions.
No further product decision is needed to start the implementation phases.
Ask the user only if implementation reveals a need to change additional supported behavior, destructively migrate data, broaden distributed scope or publish/deploy; routine API details and proportionate tests belong to the lead.
