# Workflow coverage inventory

This is an assertion-level audit of workflow lifecycle, drafts, recursive editing, provenance, and owned-source transport at revision `fcb4408dd994a31567042b691eff85f3b268c5ab`.
The audit reads test bodies and their fixtures; it does not certify that the listed tests passed in this campaign.
No tests were executed for this audit.
Parallel scheduling, HPC, Parsl, and distributed execution are excluded.
Serialized `execution: parallel` values in persistence-only fixtures do not demonstrate parallel execution and should not cause unrelated lifecycle tests to be excluded automatically.

The source-update identity concern below was resolved as ISSUE-001; current open decisions are tracked in [Campaign issues](platform-test-issues.md).
The [campaign plan](platform-test-plan.md) owns global priorities and systematic per-feature completion requirements; every remaining in-scope row is mandatory.
Every row declares its stable feature ID directly; that ID is the sole mapping key to the [obligation dashboard](platform-test-dashboard.md), while labels and row positions are descriptive only.
The `Scenario contracts` cell records all five dashboard dimensions with the dashboard state: applicable cells delegate to the row's named behavior and evidence/gap prose, while each `N` repeats its concise non-applicability reason.
Remaining gaps are proposed work, not implemented coverage.

## Selector conventions

Backend selectors below are relative to `backend/tests/` and use `file.py::test_name` after `scripts/test focus backend tests/`.
Browser selectors are relative to `frontend/tests/e2e/` and use `file.spec.ts` with the exact quoted test title supplied to `--grep`; run through `scripts/test focus e2e tests/e2e/<file> --project=chromium` first, followed by Firefox after the exact case passes.
Frontend unit selectors use their full path relative to `frontend/` plus the quoted `-t` title after `scripts/test focus unit`.
Implementation filenames without a prefix refer to `backend/src/bioimageflow_server/services/`.
Specification references are to repository-root `platform_specs_v2.md`, with `platform_specs_v1.md` sections where relevant; these internal specifications are outside the Sphinx documentation tree.
